## 0. 事实基线与适用范围

### 0.1 这套系统是什么

wx-bot（https://github.com/lawrencewzen/wx-bot）是一个把微信接到个人 AI 助手（Muse、Grok 等）的桥。微信消息经腾讯官方 ClawBot / iLink 通道进入本机 wx-bot，落盘到本地 SQLite 收件箱；助手用 `wx-bot inbox pull` 拉取，用 `wx-bot send` 发回微信。

```
微信 ──iLink──▶ wx-bot（本地收件箱）──pull──▶ 主聊（唯一处理源）
微信 ◀────────────────────────── wx-bot send ────┘
```

关键点：**没有公网端口、没有 webhook 回调地址**。所有出站能力都在本机，bridge 只监听 loopback。

### 0.2 已验证 / 未验证（截至 2026-11-06）

| 项 | 状态 |
|---|---|
| 扫码登录 | 已验证（2026-10-25 走代理通道一次通过，至 11-06 未过期） |
| 文字收发 | 已验证（10-25 至 11-02 多次 `sent`） |
| 图片收发 | 已验证（发送多次 `sent`；接收在“作为图片发送”时有文件，“作为表情包发送”时常无文件，见 18.5） |
| 服务自启 / 5 秒唤醒 / 10 分钟租约 | 有实际运行记录 |
| 虚拟机更换后自动恢复 | 已验证（2026-10-25、10-27 各一次） |
| 发送通道 502 | 尚未确诊（11-02 起几乎每次失败，11-06 20:17 起短暂恢复） |
| 工具调用类任务的端到端 | **未验证** |
| 重启持久性、去重、登录过期提醒 | **未验证**（有使用记录，无验收报告） |
| 最终交付报告（版本、通过项、停机方法、重登方法） | 尚未交付，本手册即为补齐 |

### 0.3 占位符约定

文中出现这些写法时，用你自己的值替换：

- `<home>`：你的 home 绝对路径（原环境 `<home>`）。

## 1. 设计决策（先定下来，后面不再争论）

### 1.1 决策表

| 决策 | 选择 | 原因 |
|---|---|---|
| 投递方式 | `pull`（助手主动拉），不是 `webhook`（推送） | 不对外开端口，本地 API 只监听 loopback；拉取可控、可重试、可租约 |
| 处理源 | **主聊是唯一处理源**（“主聊处理模式 v3”，2026-10-26 定） | 微信侧只转发和快速确认，不做任务、不发正式回复；所有记忆、工具、上下文都在主聊，避免两个“脑子”各说各话 |
| 回复方式 | 分两次：先一句“收到”，再发正式回复 | 用户明确要求；唤醒步骤发第一句，主聊发第二句 |
| 去重键 | `event_id` | 同一事件可能送达多次，按 event_id 去重 |
| 租约 | 10 分钟 | 超过 10 分钟的任务有重复回复风险（见 11.4） |
| 轮询 | 5 秒 | hook 每 5 秒查一次收件箱计数 |
| 看门狗 / 扫表 | 每 5 分钟 | 服务丢失自动恢复；收件箱只计数、不抢消息 |

### 1.2 三个角色

| 角色 | 触发方式 | 干什么 | 不干什么 |
|---|---|---|---|
| 唤醒转发员（hook worker） | hook 每 5 秒轮询，`count > 0` 时唤醒 | pull 事件、发“收到”、把事件全文与媒体路径写成摘要、追加对话记录 | 不做任务、不发正式回复、不改快照、不改任务状态、不 ack |
| 主聊 | 收到转发员摘要 | 读快照与共享记录、深度处理、只发正式回复、回复后 ack、更新快照与任务状态 | 不再发第二遍“收到”（除非快速确认失败）；不在主聊里闲聊式汇报 |
| 定时 worker | cron（5/10/30 分钟） | 只做检查与触发，把结果交主聊 | 不直接发微信、不改状态文件 |

这个分工的核心目的是：**租约只覆盖“主聊处理中”这一段**。转发员不 ack，主聊处理完才 ack，所以租约到期重投的风险窗口最短。

## 2. 准备工作

1. 一台能长期运行的 Linux 主机或虚拟机。原环境是 Muse 运行时里的虚拟机：home 持久化，但 `/etc` 和 `/tmp` 会在虚拟机更换时被清空（每 1–2 小时一次，见 18.1）。**这一点必须提前接受**，否则后面的自动恢复机制没有意义。
2. 一个微信号，用来扫码登录。登录后默认白名单只理会这个号。
3. 能上网的环境。如果直连出站被腾讯风控拦，准备一条代理通道（原环境就是换代理出口后扫码一次通过的，见 6.2）。
4. `sudo -n` 能无密码执行 `systemctl` 相关命令（装服务、自动恢复都要用）。没有 sudo 就换你自己的服务管理方式，后面所有 `systemctl` 步骤按等价方式替换。
5. 先读上游仓库的 `AGENTS.md` 和 `docs/agents/troubleshoot.md`。这是上游给 Agent 的操作手册，排障先查它，比猜快。

## 3. 安装与版本管理

### 3.1 安装

```bash
# 方式一：一键安装脚本
curl -fsSL https://raw.githubusercontent.com/lawrencewzen/wx-bot/main/install.sh | bash

# 方式二：源码安装（原环境用的这个）
git clone https://github.com/lawrencewzen/wx-bot ~/workspace/wx-bot
cd ~/workspace/wx-bot
./install.sh --service   # --service 同时装开机自启
```

装完确认：

```bash
ls -l ~/.local/bin/wx-bot
~/.local/bin/wx-bot --help    # v0.4.x 用这个确认命令存在
~/.local/bin/wx-bot version   # v0.5.x 用这个看版本号
```

几个坑：

- **没有 `--version` 参数**，别用。
- **`wx-bot` 不在默认 PATH 里**，所有命令写完整路径 `~/.local/bin/wx-bot`。
- `install.sh --service` 会按它自己的方式装服务。原环境最终采用的是第 5 节那份手写 unit。**两者只能留一个**：装完先 `systemctl cat wx-bot` 看清真实 unit 路径，再决定用哪份，别盲目覆盖。

### 3.2 装完应有的目录

- `~/.local/bin/wx-bot`：二进制本体。
- `~/.config/wx-bot/config.json`：主配置（0600）。
- `~/.config/wx-bot/env`：环境变量文件（0600）。
- `~/.local/state/wx-bot/`：状态与媒体。
- `~/workspace/wx-bot/`：源码仓库，排障和查文档用。

### 3.3 版本现状

- 原环境 2026-10-15 装的是 v0.4.8，2026-11-06 20:28 升到 **v0.5.1**，实测正常。
- 仓库 HEAD 当时是 `v0.4.8-1-g2fd366a`（提交 `2fd366a`，docs 精简）。
- 升级不改配置、不丢登录、不清收件箱，**不需要重新扫码**。

### 3.4 升级（v0.4.0 及以后都有 `update` 子命令）

```bash
~/.local/bin/wx-bot update
```

它会自动：下载对应平台文件 → 校验 sha256 → 替换程序 → 更新 `wx-bot-keepalive` → 重启正在运行的 systemd 服务。

实测输出（2026-11-06 20:28）：


更旧的版本会报 `unknown command "update"`，那就改用安装脚本重装。

**v0.4.8 → v0.5.1 的实际改动**（`git log v0.4.8..v0.5.1`）：CDN 媒体下载失败自动重试、异步错误记日志且不中断运行、webhook 限流 400 按 1/2/5/10 分钟重投、收件箱新增 `requeue` 命令、白名单固定为扫码本人。

### 3.5 升级后验证（缺一不可）


## 4. 配置文件

### 4.1 `~/.config/wx-bot/config.json`（0600）

```json
{
  "bindings": [
    {
      "name": "muse",
      "delivery": "pull",
      "allow_wxids": []
    }
  ],
  "local_api": {
    "listen": "127.0.0.1:18790",
    "token": "<随机长 token>"
  },
  "media_dir": "~/.local/state/wx-bot/media",
  "state_dir": "~/.local/state/wx-bot"
}
```

逐字段：

- `bindings[].name`：binding 名。`send`、`inbox`、`health` 都要带 `--binding <name>`；**`status` 不接受 `--binding`**，加了会报错。
- `bindings[].delivery`：`pull`。助手主动拉取，不用 webhook 推送。
- `bindings[].allow_wxids`：空数组 = 默认白名单，只理会扫码登录的那个号。要放行别的号见仓库 `docs/protocol.md` 第 7 节。v0.5.1 起白名单固定为扫码本人，这个字段实际已不起放行作用。
- `local_api.listen`：`127.0.0.1:18790`，只监听 loopback，不对公网开端口。
- `local_api.token`：随机 token。**不要写进文档、聊天记录、代码或日志**。丢了就重新生成并同步到所有用到它的地方。
- `media_dir` / `state_dir`：媒体与状态落盘位置。收到的图片/视频/文件在 `media/<binding>/<YYYYMMDD>/` 下。

`state_dir` 必须持久化：里面是登录态、轮询游标和 `inbox.db`，丢了就要重新扫码。

### 4.2 `~/.config/wx-bot/env`（0600）

由 systemd 的 `EnvironmentFile=-<home>/.config/wx-bot/env` 加载（前面那个 `-` 表示“文件不存在也不报错”）。内容是代理相关变量：

```
ALL_PROXY=
HTTPS_PROXY=
HTTP_PROXY=
NO_PROXY=
```

- 原环境实测：直连出口与代理出口都落在 Cloudflare 段（**两个具体 IP 已隐去**；这类信息属于敏感环境细节，转发前务必检查）。扫码走代理通道一次通过（见 6.2）。
- **手机开不开 VPN 与桥无关**：微信消息走腾讯服务器，桥能不能回复只取决于服务端 wx-bot 是否在跑。这是 2026-10-25 向用户确认过的事实，不用再问。
- 不需要代理就留空或不建这个文件。

## 5. 常驻服务（systemd）

### 5.1 unit 文件

规范备份放 `~/workspace/wx-bot-deploy/wx-bot.service`，再同步到 `/etc/systemd/system/`：

```ini
[Unit]
Description=wx-bot WeChat iLink bridge (pull delivery)
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=300
StartLimitBurst=10

[Service]
Type=simple
User=root
Environment=HOME=<home>
WorkingDirectory=<home>
EnvironmentFile=-<home>/.config/wx-bot/env
ExecStart=<home>/.local/bin/wx-bot --config <home>/.config/wx-bot/config.json run
Restart=always
RestartSec=5
TimeoutStopSec=15
KillMode=control-group
MemoryMax=256M

[Install]
WantedBy=default.target
```

要点：

- 把所有 `<home>` 换成你自己的 home 绝对路径，`User=` 换成实际运行用户（原环境是 root，因为 home 归 root 且要读写 state）。
- `Restart=always` + `RestartSec=5`：挂了 5 秒自动拉起。
- `MemoryMax=256M`：内存上限 256MB。
- `StartLimitIntervalSec=300` + `StartLimitBurst=10`：5 分钟内最多重启 10 次，防止无限重启。

### 5.2 安装与启停

```bash
sudo -n cp ~/workspace/wx-bot-deploy/wx-bot.service /etc/systemd/system/wx-bot.service
sudo -n systemctl daemon-reload
sudo -n systemctl enable wx-bot
sudo -n systemctl start wx-bot
sudo -n systemctl is-active wx-bot        # 应为 active
sudo -n systemctl status wx-bot --no-pager | head -20
```

### 5.3 备份原则

- `/etc/systemd/system/wx-bot.service` 是运行时文件，虚拟机更换会被清空。
- `~/workspace/wx-bot-deploy/wx-bot.service` 是 home 里的规范备份，不会丢。**每次改服务文件，先改备份，再同步到 `/etc`。**
- 卸载标记 `~/workspace/wx-bot-deploy/.uninstalled`：只在用户明确说“卸载/停用”时创建这个空文件。它的存在会阻止一切自动恢复（见 10.4、21）。

## 6. 登录与扫码（最容易卡住的一步）

### 6.1 登录命令

```bash
~/.local/bin/wx-bot login muse --qr-png <新文件路径> --timeout 10m
```

- `--qr-png` 后面跟一个**新文件**路径，文件名里含二维码 id。**生成的二维码图要立即发给用户，不要复制、不要重命名**（改名可能失效）。
- 二维码有效期约 2 分钟，超时重新生成。
- 用户扫码后输出 `login ok` 即成功。成功后必须做三件事，缺一不可：
  1. `sudo -n systemctl restart wx-bot`
  2. `~/.local/bin/wx-bot health --binding muse --grace 0`，退出码必须为 0
  3. 确认唤醒 hook 已启用（第 10 节）

### 6.2 风控实录（2026-10-15 → 10-25）

- 10-15：连续 3 次扫码都被拦，提示“此 OpenClaw 的运行环境存在风险，暂无法连接。”这是**服务端风控**，不是二维码的问题。
- 之后 8 天一直被拦。
- 10-25 12:05 换路线重试：走代理通道重新生成二维码（id `e80b0f65`，生成于 2026-10-25T04:06:41Z），用户扫码，约 12:08 `login ok`，一次通过。

结论：**风控拦截时不要反复扫码硬撞**。停下来、换一条出口路线再试，比连续扫码有效；连续失败就先等几小时。

### 6.3 登录前必须先做的事

**先用微信给 ClawBot 发一条消息**，助手才能回复你。不做的表现是 `send` 失败提示 `no context_token`——意思是对方还没先给 ClawBot 发过消息。这是上游 README 的原话，别跳过。

### 6.4 登录过期

- 征兆：hook 的 alert 事件提示过期，或 `status` 显示 `expired: true`，或 `send` 失败提示 `expired` / `-14`。
- 处理：重跑 6.1 生成新二维码给用户扫，成功后按 6.1 的三件事收尾。
- **登录过期提醒的正式验收：未验证。**目前靠 hook alert + 人工看 `status` 发现。

## 7. 健康检查与状态命令

**`wx-bot health --binding <binding> --grace 0` 退出码为 0 才算装好。**

```bash
# 总状态：登录、投递方式、allowlist 条数、轮询、收件箱待处理/死信
~/.local/bin/wx-bot status
# 正常要点：logged_in: true，expired: false，poll ok，inbox 0 pending / 0 dead

# 健康检查（--grace 0 = 不宽限，立即判定）
~/.local/bin/wx-bot health --binding muse --grace 0
echo $?    # 0 为健康

# 只测存活（hook 脚本里用这个）
~/.local/bin/wx-bot health --binding muse --liveness
```

- `status` 不带 `--binding`；`health`、`send`、`inbox` 都要带。
- `inbox 0 pending / 0 dead` 是常态：`pending` 是待处理事件数，`dead` 是死信数。
- 每次发完正式回复、每次处理完用户消息，顺手看一眼 `status`，确认登录没过期、收件箱已清空。

## 8. 收发命令与事件结构

### 8.1 发送

```bash
# 文字：--text - 表示从 stdin 读，适合长文本
~/.local/bin/wx-bot send --binding muse --to <wxid> --text "你好"
~/.local/bin/wx-bot send --binding muse --to <wxid> --text - < /tmp/message.txt

# 图片（--caption 会作为一条跟进文字另发）
~/.local/bin/wx-bot send --binding muse --to <wxid> --image /path/pic.jpg --caption "说明"

# 文件 / 视频
~/.local/bin/wx-bot send --binding muse --to <wxid> --file /path/doc.pdf
~/.local/bin/wx-bot send --binding muse --to <wxid> --video /path/clip.mp4
```

- `sent` = 成功；`wx-bot send: /ilink/bot/sendmessage: ret=-2 (HTTP 502)` = 上游通道故障（第 16 节）；`expired` / `-14` = 登录过期；`no context_token` = 对方还没先给 ClawBot 发过消息。
- `<wxid>` 从 `status` 的 allowlist 或事件里的 `from_wxid` 取。**不要写进文档、聊天记录或任何转发材料。**
- 发图片前先确认文件存在、大小合理。

### 8.2 收件箱（只有三个子命令）

```bash
# 只计数，不拉取、不确认、无副作用（hook 与扫表都用这个）
~/.local/bin/wx-bot inbox count --binding muse

# 拉取并加租约
~/.local/bin/wx-bot inbox pull --binding muse --lease 10m
~/.local/bin/wx-bot inbox pull --binding muse --limit 10 --lease 10m --wait 0s

# 确认
~/.local/bin/wx-bot inbox ack --binding muse muse:<event_id 数字部分>
# 成功返回 {"acked":1}
```

租约机制（非常重要）：

- `pull` 会把事件“租”走，租期内 `count` 看不到它，别的拉取者也看不到。
- **没有延长租约的命令**。到期未 ack 的事件会重新出现，可能被再次拉取、再次处理、再次回复。
- 所以：**正式回复发完后立刻 ack**；长任务超过 10 分钟一定有重复风险（11.4）。
- v0.5.1 新增 `inbox requeue`，死信可以重放。

### 8.3 事件结构

| 字段 | 说明 |
|---|---|
| `event_id` | 形如 `muse:<数字>`，去重键 |
| `kind` | `message`（用户消息）或 `alert`（wx-bot 异常：连不上微信 / 登录过期 / 已恢复） |
| `text` | 文字内容 |
| `voice_text` | 语音转写文本 |
| `media[]` | 媒体数组，每项有本机文件路径 `path` |
| `from_wxid` | 发消息人的 wxid |
| `message_id`、`to_bot_id`、`create_time`、`schema`、`has_context_token` | 原始字段，全部保留，不要丢弃 |

**未知 kind 或未知字段的处理原则（2026-10-26 定的规矩）：不要丢弃、不要猜，原样写进处理摘要交给主聊判断。**

`alert` 类事件有 `alert.message` 和 `alert.hint`，要写进摘要，但**不要回微信**——它要求主聊在自己聊天里转告。

## 9. 总体运行流程（正常的一天）

1. 用户在微信发消息 → iLink → wx-bot 落盘到本地收件箱。
2. hook 每 5 秒 `inbox count`，`count > 0` 就唤醒一个转发员。
3. 转发员 `inbox pull --lease 10m` 拉取 → 立刻发一句“收到，<用户名>”（快速确认）→ 把事件原文、媒体路径、是否已正式回复过写进摘要交给主聊 → 追加对话记录。**转发员不做任务、不发正式回复、不 ack。**
4. 主聊收到摘要 → 读快照和共享记录 → 深度处理（查资料、改图、调工具）→ 只发正式回复 → `inbox ack` → 更新快照、任务状态、对话记录。
5. 主聊在主聊里保持安静，除非异常、失败或足够重要的事需要转告（15.2）。
6. 后台定时任务照常跑：动态同步 30 分钟、Tibo 监测 10 分钟、收件箱扫表 5 分钟、服务看门狗 5 分钟。

## 10. 唤醒 hook（wechat-wxbot）

### 10.1 注册信息

| 项 | 值 |
|---|---|
| hook id | `wechat-wxbot` |
| 定义文件 | `~/hooks/definitions/wechat-wxbot.json` |
| 脚本 | `~/hooks/scripts/wechat-wxbot.sh` |
| 轮询间隔 | `poll_interval_secs: 5` |
| 脚本超时 | `script_timeout_secs: 600` |
| 投递面 | `delivery.surface: main`（唤醒主聊） |
| 展示语言 | `presentation_locale: zh-CN` |
| 状态 | `enabled: true` |

### 10.2 脚本逻辑（按执行顺序）

1. **虚拟机更换自动恢复**（见 10.4）。
2. `wx-bot inbox count --binding muse`：失败则静默上报错误，不唤醒。
3. `count > 0` 时看唤醒冷却（10.3）：冷却内且数量没变 → 不重复唤醒；否则记录唤醒时间并 `wake`。
4. `count == 0` 时清除唤醒状态文件。
5. `wx-bot health --binding muse --liveness`：健康 → 清除异常标记，静默；不健康 → 1 小时内只提醒一次。

### 10.3 唤醒冷却

- 状态文件 `~/.cache/wx-bot/hook-last-wake`，内容是“数量 上次唤醒时间戳”。
- 规则：**同一数量 120 秒内不重复唤醒**。
- 背景：2026-10-25 12:31，2 条消息连唤 5 次——第一个 worker 启动慢、租约还没生效，`count` 一直大于 0，于是每个轮询都唤醒。
- 数量变化（有新消息）或归零（都被租走）时照常唤醒。最坏情况：第一个 worker 在拉取前就死了，下一次唤醒最多晚 120 秒。

### 10.4 虚拟机更换自动恢复

三个条件**同时**满足才恢复：

1. `/etc/systemd/system/wx-bot.service` 不存在（换机清空 `/etc` 的特征）；
2. `~/workspace/wx-bot-deploy/.uninstalled` 不存在；
3. 备份 `~/workspace/wx-bot-deploy/wx-bot.service` 存在。

恢复动作：`sudo -n cp` 备份到 `/etc/systemd/system/` → `daemon-reload` → `enable`（尽力而为）→ `start` → 最多重试 4 次、每次间隔 3 秒测 `health --liveness`，通过即成功。

边界：

- 服务只是被停掉（文件还在）时**不自动重启**。停服务是人工决定，hook 不干预。
- 模拟清空测试恢复约 25 秒；2026-10-25 实测换机后约 12:34 恢复。
- 看门狗（13.3）是后备，hook 是第一道恢复。

### 10.5 异常节流

- 健康检查失败，同一问题 1 小时内只提醒一次（标记 `~/.cache/wx-bot/hook-alerted`）。
- `inbox count` 执行失败或输出无法解析时静默上报，不唤醒、不刷屏。

## 11. 主聊处理模式 v3（2026-10-26 定，取代旧模式）

### 11.1 为什么改

2026-10-26 上午实测暴露问题：用户在微信发文字 + 一个表情包，微信侧助手说“没附图”、猜用户要换头像、还发了一张黄图当 fallback。原因是微信侧助手没有上下文记忆，每条消息都要重新带图才能改图。用户原话：

> “每条新消息都要重新带图才能改，它不会自动拿上一条的图来改最后那句，所以最后那句没带图时，它又问了一次。这是为什么，没有上下文记忆吗，可以解决吗”

用户随后定调“我希望和主聊一样”，并要求“从高度、广度、深度、速度几个方面更有野心的实现”。于是改成：**主聊是唯一处理源，微信侧只转发**。

### 11.2 分工

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 唤醒转发员 | pull、发“收到”、写摘要、追加对话记录 | 不做任务、不发正式回复、不改快照、不改任务状态、不 ack 用户消息 |
| 主聊 | 读快照与共享记录、深度处理、只发正式回复、回复后 ack、更新快照与任务状态 | 不再发第二遍“收到”（除非快速确认失败）；不在主聊里闲聊式汇报 |

### 11.3 转发员 prompt 要点

完整 prompt 在 `~/hooks/definitions/wechat-wxbot.json` 的 `prompt` 字段；备份在共享记录目录的 `wechat-wxbot-prompt-backup-2026-10-26.md` 与 `...-v2.json`（可回滚）。要点：

- **必读顺序（从快到全）**：先 `wechat-context-snapshot.md`（快照），再 `wechat-core-state.md`、`wechat-tasks.md`；再 `wechat-conversation-log.md`、`wechat-media-index.md`、`~/MEMORY.md`、`~/USER.md`。简单转发只要快照 + 最近记录。
- 唤醒原因以“wx-bot 异常”开头时：不 pull、不自行重启、不回微信；跑 `health --grace 0`，对照 `docs/agents/troubleshoot.md` 判断原因，把中文原因和建议处理办法写进摘要。
- 原因是“微信有 N 条新事件”时：`inbox pull --lease 10m`，按原顺序逐条转发；`alert` 类不回微信，写清 `alert.message` 和 `alert.hint` 后 ack；其余事件捕获**全部字段**（event_id、kind、text、voice_text、media[].path 全部路径、from_wxid 及其他原始字段）。
- **去重**：先查对话记录和任务状态，该 event_id 已正式回复过 → 不再发“收到”，摘要里注明“已正式回复过，只需主聊确认”，由主聊 ack。
- **快速确认**：未正式回复过的用户消息，立刻只发一句“收到，<用户名>”。成功或失败都要记下来。
- **空图处理**：本条 media 为空但文字里说“这个”“那张”“那个表情包”时，先查快照、对话记录和图片索引，把最近一张图的信息写进摘要。**不要直接断定用户没发图，也不要让用户重发。**
- **记录**：每条处理完追加到对话记录（时间、原话、媒体路径 + 一句话描述、快速确认是否已发）；不要等主聊回复完才记；不要改快照和任务状态。
- **不要 ack 用户消息**，由主聊正式回复后 ack。
- send 失败写进摘要，不要反复重试。`no context_token` = 对方还没先给 ClawBot 发过消息；`expired` / `-14` = 登录过期，需要用户重新扫码。

### 11.4 租约与重复风险

- 租约 10 分钟是用户 2026-10-25 拍板的（从 30 分钟改小）。
- 正式回复后立刻 ack，租约就不再是问题。
- **超过 10 分钟的长任务有重复回复风险**：租约到期、事件重现，可能被再次拉取处理。兜底是按 event_id 去重（查对话记录里是否已正式回复过）。快问快答不受影响。
- 转发员不 ack、主聊 ack，这个分工就是为了把租约限制在“主聊处理中”这一段。

### 11.5 主聊处理前的必读顺序

1. `hidden_files/wechat-context-snapshot.md`（快照，先读这份）
2. `hidden_files/wechat-core-state.md`（统一事实源）
3. `hidden_files/wechat-tasks.md`（任务状态机）
4. `hidden_files/wechat-conversation-log.md`（对话记录）
5. `hidden_files/wechat-media-index.md`（图片索引）
6. `~/MEMORY.md`、`~/USER.md`
7. 动态监测另加：`hidden_files/monitoring-core-state.md`、`feed-forwarded.json`、`x-tibo-seen.json`

**只有主聊更新快照**，转发员不更新。每次正式回复后主聊更新快照、任务状态、对话记录。

## 16. 发送通道故障：HTTP 502

这是两份文档里最需要统一口径的一节。主文档（11-06 20:15）记录的是“502 期间不要重启服务”；补充文档（11-06 20:24 后）把规则改成“每次 502 先重启一次重建会话”。**最终口径以本节为准。**

### 16.1 现象

- 文字：`wx-bot send: /ilink/bot/sendmessage: ret=-2 (HTTP 502)`。
- 图片：有时是 `upload to cdn: cdn server error 500: (HTTP 502)`。
- 同时本地全部正常：`status` 显示 `logged_in: true`、`expired: false`、`poll ok`；`health --grace 0` 退出码 0；服务 `active`。

时间线：10-28 14:05 起间歇出现；11-02 约 07:44 起几乎每次失败；其间有短暂恢复（10-28 11:35–12:05、10-31 13:57–14:05、11-01 09:52–09:55 与 13:36、11-02 01:13–01:45）；11-06 20:17 起连续多次 `sent`，通道当时是通的。

### 16.2 结论

**502 是腾讯侧 iLink 发送接口返回的网关错误，不是本地配置错误。** 上游 `docs/protocol.md` 也写明：502 = “发往微信失败”，Agent 应“退避后重试”，即上游把它当偶发故障，不是配错的表现。

### 16.3 诊断顺序（照这个顺序查）

```bash
~/.local/bin/wx-bot status                            # logged_in / expired / poll / inbox
~/.local/bin/wx-bot health --binding muse --grace 0   # 退出码 0
sudo -n systemctl is-active wx-bot                    # active
```

三项都正常 → **不要动配置、不要重新登录**，按 16.4 处理。

### 16.4 处置规则（最终版）

**每次发送返回 502 后，先重启一次服务重建与腾讯的会话，再重试一次发送。**

```bash
sudo -n systemctl restart wx-bot
sleep 15
~/.local/bin/wx-bot health --binding muse --grace 0   # 退出码 0 才算好
~/.local/bin/wx-bot status                            # 确认 logged_in: true、poll ok
```

然后重试一次发送：

- 返回 `sent` → 重建会话有效。
- 仍是 502 → 说明这次不是会话问题，**继续走自动重试队列，不要反复重启**（一次就够了）。

为什么这条规则成立：重启成本十几秒，收益是“重建会话”这个唯一可能由本地触发的变量。但它不是万能的——11-02 至 11-06 的 502 期间本地一直健康，说明多数 502 与本地会话无关。**通道正常时不要重启，不要在它好的时候打断它。**

失败的条目记入待发队列，下一轮自动重试；首次失败在主聊报一次，重复失败不再报（见 22.2 第 2 条）。

### 16.5 哪些不是原因（别走弯路）

- 不是手机 VPN：手机 VPN 不影响微信桥，消息走腾讯服务器。
- 不是二维码/登录过期：`status` 会明说 `expired: true`；`send` 提示 `expired` 或 `-14` 才是过期。
- 不是 `no context_token`：那是对方还没先给 ClawBot 发过消息（6.3）。
- 不要把一次 `sent` 说成“彻底恢复”：要等下一轮试发验证。

### 16.6 重新登录：最后手段

- 触发条件：升级 + 重启都不管用，且 502 持续很久（以天计）。
- 做法：按 6.1 重新扫码，成功后重启服务、健康检查、确认 hook 启用。
- **风险必须先告诉用户**：重登要用户扫码；而且 10-15 至 10-25 有过风控连拦 8 天的前科，万一新登录也被拦，情况会更糟。所以必须用户明确同意才做，不要擅自做。

## 18. 排障

### 18.1 虚拟机更换（最常见的“故障”，其实是平台行为）

- 现象：虚拟机约每 1–2 小时更换一次，`/etc` 和 `/tmp` 被清空，home 保留。轮询随之停，期间微信消息看不到。
- 实测停滞：10-25 12:20→12:30（10 分钟）、12:47→13:29（42 分钟）。
- **诚实结论：恢复动作能在轮询恢复后几十秒内完成，但更换造成的停滞窗口无法从虚拟机内部缩短。** 不要用无效重试消耗用户耐心，直接说清窗口在哪。
- 应对：hook 自动恢复（10.4）+ 看门狗每 5 分钟（13.3）；发送文本持久化在 `hidden_files/feed-send-texts/` 而不是 `/tmp`。
- 最快补救：微信安静超过几分钟，用户在聊天里说一声，主聊马上手动查，不依赖轮询。

### 18.2 502

见第 16 节。

### 18.3 服务文件丢失 / 服务停了

```bash
ls /etc/systemd/system/wx-bot.service
sudo -n systemctl is-active wx-bot
```

- 文件丢失且无卸载标记：hook（10.4）或看门狗（13.3）会自动恢复；也可手动：

```bash
sudo -n cp ~/workspace/wx-bot-deploy/wx-bot.service /etc/systemd/system/wx-bot.service
sudo -n systemctl daemon-reload
sudo -n systemctl enable wx-bot
sudo -n systemctl start wx-bot
~/.local/bin/wx-bot health --binding muse --grace 0   # 退出码 0 才算好
```

- 服务只是停了（文件还在）：手动 `start`。hook 不会自动重启，这是有意设计。
